## 3. Human-in-the-Loop State Migration Runbook (PR 1)

All commands run from the repository root. `--dir infra` is required, because the script looks for the backend block in the folder you give it. Use `--backup-dir ./.state-backups` so the evidence lands where `tf-audit-report.sh` reads it (`<repo>/.state-backups/`). Without this flag the script writes to `infra/.state-backups/` and the audit report will show PENDING. `.state-backups/` is git-ignored.

### Phase 0: Optional negative test (sub-task 6b)

Do this before Phase A if the demo includes it. It is plan-only against the S3 backend and changes no state. See sub-task 6b in the plan file. The throwaway branch is discarded and PR 1 is built from the unmodified baseline.

### Phase A: Pre-migration backup (legacy S3 backend still configured)

The backup must come from the S3 backend. A state pulled after the `cloud` block lands comes from the new, empty workspace and is not a valid backup.

```bash
git checkout main && git status --short          # clean, on the baseline commit
eval "$(aws configure export-credentials --profile ajs-demo --format env)"

# Preview, then run
.bob/scripts/tf-cutover-verify.sh --phase backup --dir infra --backup-dir ./.state-backups --dry-run
.bob/scripts/tf-cutover-verify.sh --phase backup --dir infra --backup-dir ./.state-backups
```

Checks:
- The script prints a SHA-256 and writes `.state-backups/state-backup-<timestamp>.tfstate` (mode 600), a `.sha256` file and `cutover-evidence.txt`.
- Record the hash in your change ticket or PR.
- Optional cross-check against the reference copy `~/demo-state-backups/baseline-s3-aws4-20261110223848.tfstate` (SHA-256 `47dce3e5fa05f6504b049cbee940f0d25d92f7ae4d1284c7fdf4ee327c79b18c`): `serial` and `lineage` should match if nothing has been applied since.
- Note the `serial` and `lineage` in the backup for the write-up. This is the "before" measurement.

### Gate: PR 1 review and merge

PR 1 branch `migration/tfe-demo-cloudblk-provupgrade` changes only `infra/versions.tf`. Reviewer checks:
- The `cloud` block names `app.terraform.io`, `tce-to-tfe-migration`, `demo-cloudblk-provupgrade`.
- `required_version` still satisfies the `cloud` block and the workspace version (1.14.3).
- The provider constraint and `.terraform.lock.hcl` are unchanged.
- No secrets in the diff.

Merge PR 1, then `git checkout main && git pull`. The merge is the approval to move state.

### Phase B: State cutover (mutates state; needs `--confirm`)

```bash
terraform login                                   # or export TF_TOKEN_app_terraform_io
eval "$(aws configure export-credentials --profile ajs-demo --format env)"   # init reads the old state from S3

.bob/scripts/tf-cutover-verify.sh --phase migrate --dir infra --backup-dir ./.state-backups --dry-run
.bob/scripts/tf-cutover-verify.sh --phase migrate --dir infra --backup-dir ./.state-backups --confirm
```

- The script verifies the backup checksum first, then runs `terraform init` (a `cloud` block, so no `-migrate-state`).
- Answer `yes` when asked to copy the existing state to the new workspace. If the workspace is reported as non-empty, stop and ask: it was created empty.
- Do not run `terraform apply`.

### Phase C: Zero-diff verification

```bash
.bob/scripts/tf-cutover-verify.sh --phase verify --dir infra --backup-dir ./.state-backups
```

This runs `terraform plan -detailed-exitcode -no-color -input=false`. With a `cloud` block the plan runs remotely in HCP Terraform using the Variable Set credentials, so it is also the first test of the IAM key.

| Exit code | Meaning | Action |
| --- | --- | --- |
| 0 | `0 to add, 0 to change, 0 to destroy` | Gate passed. Continue. |
| 2 | Drift | Halt. Run section 4 (rollback). |
| 1 | Error (auth, AccessDenied, variables) | Halt and diagnose. Do not treat as pass. |

After a pass, confirm in the UI that the workspace shows 5 resources, and record:
- the new state `serial` and `lineage` versus the Phase A backup (`terraform state pull` from the new backend, then compare with `jq '{serial, lineage}'`). A change in `serial` alone is expected to be possible. A change in `lineage` is not expected. Both are unmeasured until this step.
- `cutover-evidence.txt` now holds `plan_exit_code=0`.

### Old backend retirement

Only after exit 0: keep the S3 state object and the Phase A backup until the demo write-up is done. The bucket is versioned, so nothing is lost by leaving it. Delete it only in the teardown (section 6).

## 4. Rollback Plan

Trigger: Phase B fails, or Phase C exits 2 (or 1 with an unexplained cause).

```bash
git checkout <pre-migration-commit> -- infra/versions.tf        # restores backend "s3"
eval "$(aws configure export-credentials --profile ajs-demo --format env)"
terraform -chdir=infra init -reconfigure
terraform -chdir=infra plan -detailed-exitcode -no-color        # expect exit 0 against S3

# Only if the S3 state was modified or locked:
terraform -chdir=infra state push ../.state-backups/state-backup-<timestamp>.tfstate
```

Then record the anomaly next to `.state-backups/cutover-evidence.txt` in the change ticket or PR. The workspace `demo-cloudblk-provupgrade` may now hold a copy of the state; this is harmless for the rollback, and it is cleaned up in the teardown. Do not delete it during the rollback.

Note: while the `cloud` block is active and the S3 state has not been touched, S3 remains the unchanged copy of record. The migration copies state; it does not remove the S3 object.

## 5. PR 2: AWS provider upgrade (after PR 1 is verified)

PR 2 is a separate branch (`migration/tfe-demo-cloudblk-provupgrade-aws-upgrade`) from the updated `main`. It changes `infra/versions.tf` (`required_providers`) and `infra/.terraform.lock.hcl` only.

**Open decision (human):** the target major. Registry lookup found 4.67.0 as the last 4.x, 5.100.0 as the latest 5.x and 6.72.0 as the latest overall. The upgrade guides have not been read yet, so no breaking change is claimed here. Do not choose the major until the guide for it has been read against this configuration. A 5.x target is the smaller step; 6.x may need an intermediate hop.

Steps:
1. Bob reads the upgrade guide for the chosen major and lists the entries that touch `aws_s3_bucket`, `aws_s3_bucket_public_access_block`, `aws_s3_bucket_versioning`, `aws_ssm_parameter` and `aws_sns_topic`, plus the provider block (`default_tags`).
2. Bob updates the constraint and runs `terraform init -upgrade` in `infra/` against the new backend. This needs the Phase A/B operator login (a Terraform CLI token). Bob reviews the lock file diff (version and hashes for darwin_arm64 and linux_amd64; the remote runner needs linux_amd64).
3. Bob runs a speculative plan (`terraform plan -detailed-exitcode -no-color`, remote). Exit 0 means no resource diff. Exit 2 means the PR lists every add, change, replace and destroy by address and waits for a human decision.
4. The PR description attaches the plan counts, the lock file diff summary and the guide notes. Reviewer approves in the PR.
5. After merge, the operator decides whether to run an apply from the UI. A zero-diff plan does not guarantee that state is unchanged: a provider upgrade can rewrite `schema_version` and attribute values in state on the next apply or refresh. If an apply is run for this reason, take a `state pull` backup before and after, compare them, and record what changed. Bob applies nothing.
6. If the plan shows destroy or replace, halt: do not apply. Roll back by reverting the PR 2 merge (`terraform init -upgrade` back to 4.67.0 is only safe if no apply ran; if one did, state may already be written by the newer provider and cannot be assumed to be readable by the old one, so restore from the pre-apply `state pull` backup instead).

## 6. Teardown (operator; Bob runs none of this)

Run in this order. Each step is destructive; confirm before each one.

1. Destroy the managed resources through the workspace (HCP Terraform UI: Settings, Destruction and Deletion, queue destroy plan; review and confirm), or `terraform apply -destroy` after `init`. Confirm the 5 resources are gone.
2. Empty the demo bucket `demo-cloudblk-provupgrade-ajs11102026` if destroy fails on it (it is versioned; remove all object versions and delete markers).
3. Delete the workspace `demo-cloudblk-provupgrade` and the Variable Set `demo-cloudblk-provupgrade-aws` in HCP Terraform.
4. Empty and delete the legacy state bucket `statebucket-ajs11102026`. It is versioned: delete all object versions and delete markers first, then the bucket.
5. IAM cleanup: `aws iam delete-access-key` (the key ending `CYVR`), `aws iam delete-user-policy --policy-name demo-cloudblk-provupgrade`, then `aws iam delete-user --user-name demo-cloudblk-provupgrade-tfe`.
6. Delete local copies: `.state-backups/` and `~/demo-state-backups/` (state files can contain secrets). Optionally remove the local clone.
7. Confirm in the AWS console or CLI that no S3 bucket, SSM parameter or SNS topic from this demo remains.
